The one that mattered

Nothing in the design ever made an agent start working

The spec's own model dead-ended, and it took two facts to see why.

§4 said an MCP server cannot push work into an idle session, then designed a queue whose copy promised the agent would “pick this up on its next check”. There was no next check: the four-step setup never armed one. A first-time user would link a session, press Send, and watch Queued forever — failing the spec's own headline acceptance criterion.

The premise was also wrong for Claude Code specifically. Channels do exactly what §4 says is impossible — an MCP server pushing events into a running session. The pull model is still the right v1 call (channels are research preview, Anthropic-auth only, and Cline has no equivalent), but that's a decision, not an impossibility. Separately, a tool call outliving ~2 minutes is moved to a background task, so the specced 600-second blocking long-poll is not the control flow that actually runs.

Resolved by making the state visible instead of pretending it away. A linked session that isn't watching gets a hollow chip dot rather than a solid one, and the composer says so with the exact phrase to type. Arming happens once; the tool re-arms itself after every request.

Critical defects

Two inherited, two of my own

Critical Pre-existing Whole-block save was a source-injection primitive

applyStyleBlock spliced client text into the .svelte file verbatim. A payload containing </style> closed the block early and everything after it became markup or script — under SSR, code execution in the dev server. postcss parses such a string happily, so the completeness check never caught it. Reachable from any page before the origin guards landed.

Fixed. Refused before the write, with the obfuscated spellings covered. The sibling /apply and /edit paths were verified safe — postcss escapes the < when it re-serializes.

Critical Mine The agent token was served over HTTP

I put the lockfile at <root>/node_modules/.stylewright/dev.json, as the spec specified. That path is inside the tree Vite serves, so the dev server handed the bearer token to any unauthenticated GET — verified live with curl. The 0600 mode I'd added was irrelevant; the leak was over the network, not the filesystem.

Fixed. The token now lives only in a user-level registry outside the root, plus fs.deny as defence-in-depth for files an older version may have left behind. The registry is also the more capable option — it's what makes monorepo layouts work.

Critical Mine A dying agent silently swallowed the next request

The liveness design hung on req.on('close'), attached after the body was already drained — by which point Node had emitted it. So a killed agent still read as watching, the next Send was handed to a socket nobody was reading, and the panel showed working forever for a run no agent ever saw.

Fixed. Liveness now hangs off the response, and a claim that resolves onto a dead socket is put back on the queue rather than lost. Pinned by an end-to-end regression test that aborts a real claim mid-flight.

High Pre-existing The whole overlay was rendering in Times

:host { all: initial } resets font-family to the browser default, and nothing re-established it — so every element that didn't name a family inherited serif, including the existing panel header. IBM Plex was loading fine and going unused.

Fixed in one line in the shadow stylesheet, which repairs the existing chrome as well as the new tab.

Three agents, one table

And what measuring OpenCode turned up

Every client kills a blocking tool call eventually, and they disagree about when, in what unit, and whether you can change it.

That number was scattered across the MCP process, the broker and the overlay — which is how the overlay once told Cline users to run a claude command. It now lives in one file, src/shared/vendors.ts, and everything else is derived from it: the watch budget, the session badge, the setup steps, the generated config, and the sentence naming which tools are on offer. Adding a vendor is an entry in that table and nothing else.

Settings → Agents lists all three with a switch and a Setup button each. The switch only controls whose instructions you are shown — any MCP client that speaks the protocol still connects. The preference is stored as the disabled list, so a vendor added in a later release appears for people who already have settings saved instead of staying invisible.

WrongThe research said OpenCode ignores per-server timeouts. It does not.

I built the first OpenCode entry on the claim that its timeout governs discovery only, that execution is capped near 30 seconds, and that overrides are ignored — so the entry shipped no timeout at all and a deliberately short 25-second watch.

Measured against the real 1.18.4 binary: a timeout of 3000 ms killed an 8-second call, no timeout killed a 70-second one at ~30 s, and a timeout of 90000 ms let the same 70-second call through. The setting is honoured, it is in milliseconds — unlike Cline's, which is in seconds — and the entry now ships it.

FixedThe generated config asked for 59 minutes; the process silently gave 25

Both file-configured vendors write STYLEWRIGHT_WATCH_MS into the config the overlay tells you to paste. The MCP process clamped that value to a fixed 1,500,000 ms ceiling — so the watch ended less than halfway into the tool timeout it had been matched to, and the arming the hour-long timeout was meant to buy expired anyway.

The ceiling is now derived from the vendor table, so a config we generate can never be capped below the number we just told someone to paste. A test asserts it per vendor.

NewThe watch heartbeats, so short client timeouts stop mattering

Reading OpenCode's bundle turned up resetTimeoutOnProgress on its tool calls: the request timer restarts on every progress notification. stylewright_watch now emits one every 10 seconds while it blocks — but only when the client supplied a progress token, since sending progress for a token nobody issued is a protocol error elsewhere.

Confirmed live: an OpenCode-identical client held a watch for 70 seconds through seven heartbeats, past the ~30-second cap it would otherwise have hit, and took the request the browser sent.

Fixed“That session isn’t watching” — shown while it was working on your task

A session that has just taken a request stops watching until it re-arms. The nudge fired in that window, directly beneath a card saying the same session was running the request. It reads as a bug in the panel and sends you off to retype an instruction the agent does not need. It is now suppressed while a request is in flight, and returns if the session goes quiet afterwards.

How the two review passes worked

Both passes used the same shape: independent reviewers over separate lenses, then a second adversarial agent per finding whose job was to refute it by opening the files itself — defaulting to “refuted” unless it could confirm the claim in the source.

The first pass audited the handoff against the repo: 43 candidate disagreements, 27 survived. The second reviewed my own implementation across six lenses: 29 candidates, 25 survived. The refuted ones mattered too — they stopped me from “fixing” three things that were already correct, including a suspected undo-timeline regression that the existing dedupe already prevented.

The token leak and the lost-request bug both came out of the second pass. Neither would have been caught by the test suite as I'd written it, because both were failures of a premise I held while writing the tests.
